NineLives

A crash-safe key-value database in Go, standard library only, and a torture tool that SIGKILLs it at random moments to prove that no acknowledged write is ever lost.

$ install

Needs Go 1.27 or newer and Linux or macOS. Nothing else: no dependencies, no services, no network. Windows is not supported, because it cannot rename over an open file and has no directory fsync, and the durability story depends on both.

  1. Clone the repository.

    $ git clone https://github.com/ANI-CPU-tech/TheSONions_Srinathon.git
$ cd TheSONions_Srinathon

  2. Build. One script, two binaries in bin/.

    $ scripts/build.sh
built bin/ninelives and bin/torture

  3. Store something and read it back. The database is the file you name; it is created on first use.

    $ ./bin/ninelives put my.db greeting hello
OK seq=1
$ ./bin/ninelives get my.db greeting
hello

  4. Kill it and prove it: run the torture tool with any seed.

    $ ./bin/torture --seed 4242 --iterations 50

  5. Optional: run every test.

    $ go test ./...

How you use it from your own program: through the CLI, or by starting ninelives serve as a child process and talking to it over stdin/stdout, which works from any language. The Go module is named ninelives, not a URL, so it cannot be fetched with go get.

$ cat GUARANTEES

  1. An OK means it is on disk. put, del and batch return success only after the record is written and fsynced. A printed OK seq= or ACK survives the process dying one millisecond later.
  2. A batch is all or nothing. A batch is one record with one CRC. After a crash it is either fully there or not there at all, and readers never see half of it.
  3. Recovery keeps every acknowledged record. Bytes from an interrupted write (a torn tail) are cut off, never guessed at. Cutting is idempotent: kill open during recovery and the next open simply does it again.

keys and values

Plain text with no spaces is used as is. For any bytes at all, write x: and lowercase hex: x:00ff is two bytes, x: alone is the empty value. dump prints text when every byte is printable, hex otherwise, so output can be fed straight back in.

batch files

One op per line, put <key> <value> or del <key>. Blank lines and # comments are skipped. Ops apply in order, so the last op on a key wins. One bad line rejects the whole file and nothing is written.

put k1 v1
put k2 v2
del k1

$ ninelives serve my.db

serve opens the database once (running recovery) and answers one request per line. Every response is one line, flushed at once. This is how the torture tool drives the database, and how another program can embed it.

requests

[@w:id] put <key> <value>
[@w:id] del <key>
[@w:id] get <key>
[@w:id] batch <n>     # then n op lines
[@w:id] compact
[@w:id] stats

responses

READY keys=.. recovery_ms=..
ACK <opid> <seq>
VAL <opid> <value>
NOTFOUND <opid>
STATS <opid> keys=.. file_bytes=.. dead_bytes=..
ERR <opid> DISKFULL|BADREQ|TOOLARGE|FAILED ..
  • ACK is printed only after the write was fsynced.
  • ERR means nothing was written.
  • The @writer:opid prefix is optional, so you can type requests by hand. Each writer id gets its own queue: one writer's ops run in order, different writers run concurrently.
  • Values up to 1 MiB, batches up to 10,000 ops.
  • On end of input (Ctrl-D), ops in flight finish, the file is closed, exit 0.

$ xxd demo.db

One file is the whole database: a 24-byte header, then records until the end. Integers are little-endian. A record counts only if all its bytes are there and its CRC32-C matches; that check is what makes a half-written record detectable. what open() does

  1. Delete leftover <path>.compact and <path>.init; they are never trusted.
  2. No file yet? Write the header to <path>.init, fsync, rename it into place, fsync the directory.
  3. Check the header: magic, version, CRC.
  4. Scan records from byte 24. Stop at the first one that is short, has an impossible length, or fails its CRC.
  5. If bytes remain after the last good record, truncate them and fsync.

Every acknowledged record was fsynced before its OK, so it always sits before any torn tail and is never cut.

$ ./bin/torture --help

The torture tool is how we prove the guarantees instead of asserting them. Each iteration does this:

  1. startninelives serve on the database
  2. writetwo writers send ops; oracle.log records every send and every ACK
  3. killSIGKILL after a random 1–400 ms
  4. recoveropen, check, dump: recovery runs here
  5. verifycompare the dump with the oracle log, then go again from 1

The oracle never asks the database what it should contain. It records each op when sent and each ACK when received, independently. After the kill, every acknowledged write must be in the dump, a batch must be all there or all absent, and any value the tool never wrote is a failure. Every value carries a tag (w<writer>o<opid>:) so it can be traced to exactly one op.

testing the tester

A tool that always says PASS proves nothing. torture/fakeserve speaks the serve protocol but can lie on purpose, and the oracle must catch every lie:

--bugthe lieexpected
drop-ackACK an op without writing itFAIL
partial-batchACK a batch after writing only part of itFAIL
garbageadd a key/value nobody wroteFAIL
staleACK a put but store a wrong valueFAIL
nonehonestPASS
 
$ go build -o bin/fakeserve ./torture/fakeserve
$ ./bin/torture --seed 11 --iterations 5 --bin ./bin/fakeserve --bug drop-ack

$ NINELIVES_CRASH_AT=…

Random kills find problems; named kills explain them. The engine can SIGKILL itself at 13 exact places, a real kill and not a clean exit. Set NINELIVES_CRASH_AT to the name, and optionally NINELIVES_CRASH_AFTER=N to die on the Nth hit.

$ go test ./tests/engine -run Million -v

One million keys written as one million separate PUT records (11-byte keys, 100-byte values, a 127 MB file), then open() from scratch. The requirement is under 2 seconds.

Measured on a laptop with a warm page cache (the file was just written). A cold cache was not measured. Recovery is one sequential scan through a 1 MiB buffer, and the index stores file offsets, never copies of values.

compaction at scale

One million puts plus one million deletes, in batches of 10,000, then compact: about 2 seconds, and the file shrinks from 23 MB to 24 bytes, the bare header. Compaction also runs on its own once the file is at least 4 MiB and more than half of it is dead.

$ ls scripts/

Two helpers for trying everything by hand. Both print the exact command they run, so every step can be retyped without them.

nlshell: the test menu

An interactive prompt. Type / and the commands appear; Tab completes, arrows pick, Enter runs. Arguments complete too: torture modes and crash-point names.

  • /put a 1, /get a, /batch put c 3; del c, /dump: the CLI on a scratch database
  • /crash mid_write: kill at a crash point, then recover
  • /serve: talk to serve by hand, !kill sends a real SIGKILL
  • /torture compaction, /torture-all, /selftest
  • /test, /test-crashpoints, /test-recovery-1m
$ go build -o bin/nlshell ./scripts/nlshell && ./bin/nlshell

nlui: the lab window

The same commands in a local browser window. For each run it shows the command and its output, what changed in the file, record by record, and the code path it took through the engine.

  • Tabs: CLI, Serve + kill, Crash lab (all 14 scenarios), Torture, Build + tests
  • Watch mode: run ninelives in any terminal and see each change appear in the window
  • Listens on 127.0.0.1 only, needs no network; the page is built into the binary
$ go build -o bin/nlui ./scripts/nlui && ./bin/nlui

$ cat LIMITS

What we have not proven, stated plainly:

  • Power loss was not tested. Kills are process kills (SIGKILL); the data is fsynced, but no machine was unplugged.
  • Tested on Linux only. macOS should behave the same and has not been run.
  • Two of the 32 scenarios are not verified: a kill inside close(), and a get during a batch. The mechanism exists; no test proves it yet.
  • No file lock: one process writes a database file at a time.
  • 1M-key recovery was timed with a warm page cache only.
